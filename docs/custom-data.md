# Custom data systems

Substance has two separate extension systems. Mob equipment is data-driven at runtime and can be extended by datapacks. Loot and trader patches currently use a Java registry populated during initialization; their JSON codec classes document a planned/experimental format but are not automatically loaded from datapacks in this release.

## Mob equipment reload data

Files are read from:

```
data/<namespace>/mob_equipment/<name>.json
```

The built-in files use the `substance` namespace. A datapack can use its own namespace and add additional files. Each file has two required fields:

```json
{
  "entities": ["#substance:zombies", "minecraft:wandering_trader"],
  "equipment": {
    "mainhand": "substance:cigarette"
  }
}
```

### `entities`

`entities` is a list of entity IDs or entity-type tags.

- An entity ID is written as `namespace:id`, for example `minecraft:zombie`.
- A tag is prefixed with `#`, for example `#substance:zombies`.
- Invalid IDs are logged and ignored. A file with no valid entity or tag entries is skipped.

### `equipment`

`equipment` maps a vanilla equipment-slot name to an item ID. Valid slot names include `mainhand`, `offhand`, `head`, `chest`, `legs`, and `feet`. Item IDs are normal registry IDs such as `substance:herbal_roll` or `minecraft:carved_pumpkin`.

Definitions are sorted by descending priority and then by resource ID. The normal mob-equipment rules still decide whether an entity can receive the item and whether its hand is empty. Reload resources with `/reload` after changing a datapack.

## Datapatch registry

Loot-table patches and merchant offers are currently registered by Java code in `DatapatchRegistry` and loaded by `DatapatchLoader` during mod initialization. The three supported definition types are:

- `LootEntryDef`: adds an item to a target loot table, with weight and a uniform min/max count.
- `VillagerTradeDef`: adds a trade to a profession and villager level.
- `WanderingTraderTradeDef`: adds a trade to a wandering-trader pool.

The registry groups loot entries by target table, villager trades by profession and level, and wandering trades by pool. Loot entries are applied through Fabric's loot-table modify event. Villager trades are registered through Fabric's `TradeOfferHelper`.

The internal JSON records (`LootPatchJson`, `VillagerTradeJson`, and `WanderingTraderTradeJson`) describe the serialized shape being considered for a future fully data-driven implementation. They are not a supported datapack API in the current release. Do not place those files in a datapack and expect them to be discovered automatically.

## Generated recipes and data

Recipe, model, tag, loot-table, and advancement files are generated by the Fabric datagen entrypoint. Run the `datagen` Gradle run configuration when changing recipe definitions, then review generated files under `src/main/generated` before committing them. Create-specific recipes are conditioned on the Create mod being loaded; vanilla replacement recipes use the inverse condition.

## Compatibility guidance for datapack authors

- Use namespaced IDs everywhere; do not rely on implicit `minecraft` IDs.
- Keep custom files in your own namespace to avoid collisions.
- Test `/reload` and a fresh world after changing mob equipment files.
- Do not overwrite Substance's built-in files unless you intentionally want to replace them.
- Treat the datapatch JSON records as experimental until a future release exposes a resource reload listener for them.
